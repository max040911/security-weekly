XZ Utils 後門：一場花了兩年的開源供應鏈攻擊

  • CVE-2024-3094
  • 供應鏈攻擊
  • Linux

本期三句話

  1. xz 5.6.0 與 5.6.1 被植入後門，可能讓攻擊者遠端控制 SSH。
  2. 攻擊者花了約兩年經營信任，成為專案的共同維護者後才下手。
  3. 主要影響測試版發行版；確認 xz 不是這兩個版本即可。

深講：信任，才是被攻破的那一層

先備概念

想像一棟大樓的門禁系統，用的是某家小工廠做的零件。大樓很注重保全，但沒人想到，那家小工廠的老闆換人了，新老闆在零件裡藏了一把萬用鑰匙。

xz 是 Linux 上很常見的壓縮工具，它的函式庫 liblzma 被許多程式間接使用。這種「你沒直接裝，但它就在你系統裡」的元件，就是軟體供應鏈（software supply chain）的一環。攻擊供應鏈的好處是：只要污染一個上游，所有下游都會自動收到。

另一個關鍵是：很多開源專案只靠一兩位志工維護，他們很累、很需要幫手。這次攻擊，利用的就是這一點。

事件經過

  1. 2021 年起名為「Jia Tan」的帳號開始對 xz 專案提交修補，表現積極可靠。
  2. 2022 年數個疑似分身帳號在郵件論壇抱怨進度太慢、施壓原維護者 Lasse Collin 增加維護者。Jia Tan 逐步取得發布權限。
  3. 2024-02xz 5.6.0 發布，隨後 5.6.1 發布，兩版都含後門。
  4. 2024-03-29工程師 Andres Freund 發現 SSH 登入異常變慢、CPU 用量偏高，追查後在 oss-security 郵件論壇公開揭露。
  5. 2024-03-29美國 CISA 發布警示，建議降版至未受影響版本；各發行版迅速撤回。

技術機制

後門設計得非常隱密，有三個值得注意的地方：

  • 不在 Git 原始碼裡：惡意的建置腳本只出現在發布用的 tarball 中。只看 GitHub 上原始碼的人看不到。
  • 藏在測試檔裡：真正的惡意程式碼被包裝成「用來測試壞掉壓縮檔」的二進位測試資料，看起來完全合理。
  • 借道 systemd 碰到 SSH：OpenSSH 本身不用 liblzma，但部分發行版讓 sshd 連結 libsystemd，而它又連結 liblzma。後門因此能在 sshd 載入時，攔截它驗證 RSA 金鑰的函式。

概念上的依賴鏈如下（示意）：

sshd  ──連結──▶  libsystemd  ──連結──▶  liblzma (被植入後門)
                                         │
                       建置時注入，執行時攔截 RSA 驗證函式
                                         ▼
                 持有特定私鑰的攻擊者 → 可在目標上執行指令

只有持有特定私鑰的攻擊者能觸發，其他人連掃描都看不出來。這也是它被評為 CVSS 10.0 的原因。

防禦與啟示

立即可做

  • 執行 xz --version，確認不是 5.6.0 或 5.6.1。
  • 用穩定版發行版的主機基本不受影響；用測試版（如 Debian unstable、Fedora Rawhide）的要更新。

長期該想

  • 「發布檔」與「原始碼」不一致是警訊，可重現建置（reproducible builds）能抓到這種差異。
  • 維護者過勞是資安問題：支持你依賴的開源專案。
  • 這次是靠一個人的好奇心才發現，效能異常也值得追查。

名詞小卡

供應鏈攻擊（supply chain attack）
不直接攻擊目標，而是污染目標所依賴的上游元件。
後門（backdoor）
刻意留下、可繞過正常驗證的隱密入口。
Tarball
以 .tar.gz 等格式打包的發布檔，常被發行版拿來建置套件。
可重現建置（reproducible builds）
同一份原始碼不論誰來建置，產出都逐位元相同，因此能驗證發布檔未被竄改。
CVSS
通用漏洞評分系統，0–10 分，10 分代表最嚴重。
